# 6. CORRECCIÓN CRÍTICA 02 — ELIMINAR LA CONTRADICCIÓN DEL COSTPRESENTER

## ARCHIVOS AFECTADOS

- `01-requirements.md`
- `02-static-architecture.md`
- `03-dynamic-architecture.md`
- `04-api-contract.md`
- `05-implementation-plan.md`
- `06-test-specification.md`

### PROBLEMA CONFIRMADO

El proyecto pretende soportar topologías válidas arbitrarias.

Sin embargo, la presentación de la métrica `loss` incorpora límites:

`PRESENTER_MAX_TERMS = 2048`

`PRESENTER_MAX_BITS = 200000`

Si se superan, el Controller puede devolver HTTP 500 aunque Bellman-Ford haya calculado una ruta válida.

**ESTO NO DEBE QUEDAR SIN RESOLVER.**

### ORDEN OBLIGATORIA

Debes rediseñar esta parte buscando la solución más sencilla que conserve:

1. Correcta selección de rutas.
2. Las tres métricas oficiales.
3. Desempate determinista documentado.
4. Representación numérica definida.
5. Consistencia con la API.
6. Comportamiento controlado ante entradas válidas.
7. Complejidad razonable.
8. Viabilidad de implementación.

### ANÁLISIS MATEMÁTICO OBLIGATORIO

Estudia la separación entre:

**Cálculo de la ruta óptima:** requiere respetar la política de comparación del algoritmo.

**Presentación del costo:** requiere comunicar el resultado con una precisión y representación documentadas.

No exijas a la presentación mayor exactitud que la necesaria para el contrato si ello obliga a implementar cálculos excesivamente complejos.

Para `loss`, compara alternativas numéricamente estables, como la evaluación de `-ln(1-p)` mediante funciones adecuadas, representaciones decimales o procedimientos de aproximación con error controlado.

Si conservas productos racionales de probabilidades de supervivencia para comparar rutas, formaliza cómo se obtiene y presenta el costo logarítmico sin alterar la selección.

### DECISIÓN TÉCNICA OBLIGATORIA

Selecciona una única política y justifícala mediante:

- Correctitud.
- Complejidad.
- Dominio admitido.
- Precisión garantizada.
- Tratamiento de extremos.
- Terminación.
- Errores controlados.
- Tiempo de implementación.
- Compatibilidad con las tres métricas.

No aceptes una solución que reintroduzca el problema de las pérdidas extremadamente pequeñas.

No aceptes límites arbitrarios que contradigan las entradas declaradas válidas.

Si son imprescindibles límites de entrada o de recursos, deben quedar definidos antes del cálculo, ser compatibles con los requisitos oficiales y tener errores documentados. No puede ocultarse la limitación detrás de un `500 INTERNAL_ERROR` genérico.

### CRITERIO DE CIERRE

Debe existir una política numérica única, reproducible y viable.

La arquitectura no debe obligar a implementar una biblioteca matemática desproporcionada para un taller de 108 minutos.
